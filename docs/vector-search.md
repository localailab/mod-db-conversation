# ベクトル検索（Ollama + LanceDB）

conversation-memory の意味検索のしくみと設定。modの使い方は [README](../README.md) を参照。

## 全体像

```
保存時:  メッセージ ──[Ollama: bge-m3]──→ ベクトル ──→ LanceDB（~/.claude-memory/vectors）
検索時:  検索語やプロンプト ──[Ollama: bge-m3]──→ ベクトル ──→ LanceDBで近いものを探す ──→ 本文はSQLiteから引く
```

| 役割 | 使っているもの |
|---|---|
| 文章をベクトルに変換する（埋め込み） | [Ollama](https://ollama.com) + `bge-m3` |
| ベクトルを保存して、近いものを探す | [LanceDB](https://lancedb.com)（組み込み型。サーバーは不要） |
| 会話の正本、キーワード検索 | SQLite（FTS5） |

LanceDBは、ベクトルを保存して探すだけで、文章をベクトルに変換する機能は持っていない。その変換を、手元で動かすOllamaが担当する。

### この組み合わせにした理由

- **LanceDB**: SQLiteと同じくファイルとして置くだけで使える。DBサーバーを立てなくていい
- **Ollama**: モデルを読み込んだまま待機するので、1回の変換が数十msで終わる。CLIは呼ばれるたびに起動し直すので、CLIの中でモデルを読み込むと毎回1〜数秒かかってしまう
- **bge-m3**: 日本語に強い多言語モデル。日本語と英語が混ざった会話でも検索できる
- 会話の内容が外部のAPIに送られない

## セットアップ

```bash
ollama pull bge-m3      # 約1.2GB
```

Ollamaは起動したままにしておく。Macなら、Ollamaアプリをログイン時に自動で起動する設定にしておくといい。

これまでの会話をベクトル化する:

```bash
node dist/cli.js embed      # または npm run backfill（取り込みとベクトル化をまとめて行う）
```

約300件で10秒ほど。

## いつベクトル化されるか

- **会話の保存時**（modの `Stop` / `PreCompact` / `SessionEnd`）: transcriptを取り込んだあと、新しいメッセージをベクトル化する。hookを待たせすぎないように、1回あたり最大200件、8秒までにしている。残りは次の保存時に処理される
- **セッション開始時**: `cli.js warm` でモデルをOllamaに読み込ませておく。最初のプロンプトで読み込みを待たされないようにするため
- Ollamaには `keep_alive: 30m` を指定していて、使っている間はモデルが読み込まれたままになる

どのメッセージを、どのモデルでベクトル化したかは、SQLiteの `messages.embedded_model` に記録している。値がNULL、または今のモデルと違うメッセージが「未処理」になる。

## Ollamaが止まっているとき

- 保存とキーワード検索はそのまま動く
- ベクトル化できなかったメッセージは未処理のまま残り、Ollamaが動き出したあとの保存時（または `cli.js embed`）にまとめて処理される
- 未処理があるあいだは、プロンプトの下のステータス行に「N件がOllama待ち」と表示される
- 検索結果の `semantic` に、意味検索を使えなかった理由が入る（例: `unavailable: fetch failed`）

## ハイブリッド検索

キーワード検索と意味検索の両方を行い、順位ベースで混ぜる（Reciprocal Rank Fusion、k=60）。各結果の `match` に、どちらでヒットしたか（`keyword` / `semantic`）が入る。意味検索でヒットしたものには、コサイン距離 `distance`（0に近いほど近い）が付く。

| | キーワード | 意味（ベクトル） |
|---|---|---|
| 仕組み | SQLite FTS5（trigram）、bm25で順位付け | bge-m3のベクトルのコサイン距離 |
| 得意なこと | 固有名詞、コード、ファイル名 | 言い換え（「チャットを削除」→「廃止したい」）、日本語と英語の混在 |
| 対象 | メッセージすべて（tool呼び出しと結果はデフォルトで除外） | 20文字以上のテキストメッセージ |

### 検索の入口と基準

| | `search`（Claudeのtool、`/recall`） | `related`（プロンプトごとの自動添付） |
|---|---|---|
| キーワード | スペース区切りの語をすべて含む（AND） | プロンプトのtrigram（ひらがなだけのものを除く）の25%以上を含む |
| 意味 | 距離0.45以下 | 距離0.33以下 |
| 件数 | デフォルト10件 | 最大3件 |
| 意味検索の待ち時間の上限 | 5秒 | 2秒 |
| 考え方 | Claudeが距離を見て判断できるので、ゆるめ | 頼まれていないのに添付するので、厳しめ |

### しきい値の決め方

bge-m3で実際の会話を測って決めた。

| 検索した文 | 結果 |
|---|---|
| 「右端のチャット欄のデザインってどうなってたっけ？」 | 関連する会話が距離0.24〜0.40 |
| 「チャットウィジェットを削除した件」 | 「そのチャットをこのサイトから廃止したいです」が距離0.26（文字はほとんど重ならない） |
| 「ありがとう」「今日はいい天気ですね」 | 「お願いします」「これめっちゃいいよありがと」などの短い雑談が距離0.28〜0.34 |

短い雑談同士が近いと判定されるので、20文字未満のメッセージは意味検索の対象から外している。自動添付の0.33は、関連する会話の上位だけが通る値にしている。

しきい値は `src/search.ts` の先頭にまとめてある。

```ts
const SEMANTIC_MIN_CHARS = 20;
const SEARCH_MAX_DISTANCE = 0.45;
const RELATED_MAX_DISTANCE = 0.33;
const RRF_K = 60;
```

## 速度

| 処理 | 時間（M系Mac、モデル読み込み済み） |
|---|---|
| 検索語1つのベクトル化 + LanceDB検索 | 約50ms |
| 自動添付1回（CLIの起動を含む） | 約0.2秒 |
| 既存メッセージ約300件のベクトル化 | 約10秒 |

## データ

```
LanceDB（~/.claude-memory/vectors）
messages_<モデル名>
  id          = SQLiteの messages.id
  project_id  検索をプロジェクトで絞るため
  session_id  今のセッションの除外と、削除のため
  vector      bge-m3なら1024次元
```

- ベクトルは、テキストのメッセージ1件につき1つ。本文の先頭2000文字から作る
- LanceDBに本文は置かない。検索でヒットしたidを使って、本文はSQLiteから引く
- 同じidは上書きされる（`mergeInsert`）。同時に複数のセッションから保存しても重複しない
- `delete_session` は、SQLiteとLanceDBの両方から消す

## モデルを変える

```bash
ollama pull <モデル名>
export CONV_MEMORY_EMBED_MODEL=<モデル名>
node dist/cli.js embed
```

ベクトルはモデルごとに別のテーブル（`messages_<モデル名>`）に入る。次元数の違うモデルに変えても混ざらない。しきい値はモデルによって変わるので、変えたら測り直す。

## 環境変数

| 変数 | 内容 | デフォルト |
|---|---|---|
| `CONV_MEMORY_VECTORS` | LanceDBのディレクトリ（指定の仕方は [README](../README.md#データの保存場所)） | `~/.claude-memory/vectors` |
| `CONV_MEMORY_EMBED_MODEL` | Ollamaの埋め込みモデル | `bge-m3` |
| `OLLAMA_HOST` | Ollamaの場所 | `127.0.0.1:11434` |

## 関連するファイル

| ファイル | 内容 |
|---|---|
| `src/embed.ts` | Ollamaの `/api/embed` を呼ぶ |
| `src/vectors.ts` | LanceDBへの保存、検索、削除。未処理メッセージのベクトル化 |
| `src/search.ts` | ハイブリッド検索（キーワード検索、意味検索、RRF） |
